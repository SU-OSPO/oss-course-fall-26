1. Continuous integration: automatically running unit tests

In this tutorial you will add unit tests to a simple Python package, then write a GitHub Actions workflow that automatically runs those tests every time you open or update a pull request. This is known as continuous integration (CI). Nearly every open source project of any size uses some form of CI, since it lets maintainers know right away whether a contribution breaks anything.

For this exercise we’ll use a toy Python package that I created called toymath. It contains a couple of functions for doing (very) simple math.

I. Set up the repository

1. Fork, clone, and create a branch

CautionChallenge

Use what you learned in the git and GitHub tutorials to:

  1. Create a fork of https://github.com/SU-OSPO/toymath under your GitHub account.

  2. Clone your fork to your local computer.

  3. In your local repository, create and switch to a new branch called add-ci-tests.

Try to do this on your own. If you can’t remember how, refer back to Part 2 and Part 3 of the git tutorials. If you’re still stuck, expand the solution below.

CautionSolution

  1. Go to https://github.com/SU-OSPO/toymath and click the Fork button in the upper right. On the “Create a new fork” page, select your username under “Owner” and leave the repository name as toymath. Click the green Create fork button. You’ll be redirected to your fork, which will have a URL like https://github.com/YOUR_USERNAME/toymath.

  2. On your fork’s webpage, click the green <> Code button, select the “SSH” tab, and copy the URL. It should look like git@github.com:YOUR_USERNAME/toymath.git. Then, in a terminal, cd to the directory you’d like to keep the repository in and run:

    git clone git@github.com:YOUR_USERNAME/toymath.git
cd toymath

    (If you’re using VS Code for authentication instead of an SSH key, copy the HTTPS URL instead and use the “Git: Clone” command in the command palette, as described in Part 2 of the git tutorials.)

  3. Run:

    git checkout -b add-ci-tests

    You can verify you’re on the new branch by running git branch.

Take a look around the repository. The package’s source code is in the toymath directory. The functions we care about are in toymath/functions.py:

"""Basic arithmetic functions."""


def add(a, b):
    """Return the sum of a and b."""
    return a + b


def subtract(a, b):
    """Return a minus b."""
    return a - b

There’s also a pyproject.toml file, which tells pip how to install the package (we covered this in the packaging and deployment lecture). Notice what’s not there: any tests!

2. Create a conda environment and install toymath

Let’s create a new conda environment to develop toymath in. From the toymath directory, run:

conda create -n toymath python=3.13
conda activate toymath

Now install toymath into the environment:

pip install -e .

The . tells pip to install the package in the current directory. The -e flag installs it in editable mode. This means that rather than copying the source code into your environment, pip points the environment to the source code in your repository. That way, any changes you make to the code will be picked up immediately, without having to re-install the package. This is what you usually want to do when developing a package.

To check that the install worked, try out the command-line program that comes with toymath:

toymath_calculator add 2 3

You should get back 5.0.

II. Write and run unit tests

3. Write a test

We’ll use pytest to test our code. pytest looks for files whose names start with test_, then runs any function in those files whose name starts with test_. If the function runs without error, the test passes. If it raises an error, the test fails. Typically, tests use Python’s assert statement to check that a function returns what we expect; assert will raise an error if the statement following it is False.

  1. In the top level of your repository, create a directory called tests:

    mkdir tests

  2. Use your favorite text editor to create a file called tests/test_functions.py and put the following in it:

    """Unit tests for the functions in toymath."""

from toymath import add, subtract


def test_add_subtract_roundtrip():
    """Check that subtracting a from the sum of a and b gives back b."""
    for a, b in [(3, 5), (-2, 7), (10, 0)]:
        c = add(a, b)
        assert subtract(c, a) == b

    This is called a round-trip test: we add two numbers a and b to get c, then subtract a from c. If both add and subtract are working correctly, we should get back b. We do this for a few different pairs of numbers to make sure it isn’t working just by chance.

4. Run the tests

  1. Install pytest into your environment:

    pip install pytest
    Tip

    Take a look at pyproject.toml. You’ll see a [project.optional-dependencies] section with test = ["pytest"]. This is a common way to list the extra packages that developers need to run the tests. Instead of installing pytest directly, you could have run pip install -e ".[test]", which would install toymath along with everything in the test list.

  2. From the top level of your repository, run:

    pytest

    pytest will find your test and run it. You should see something like:

    ============================= test session starts ==============================
...
collected 1 item

tests/test_functions.py .                                                [100%]

============================== 1 passed in 0.01s ===============================

    The . after the file name means the test passed. Congratulations, you’ve written and run your first unit test!

  3. Commit your new test:

    git add tests/test_functions.py
git commit -m "add round-trip test for add and subtract"

III. Create a GitHub workflow to run the tests

Running the tests on your own computer is great, but it relies on everyone remembering to do it. It also only tells you whether the tests pass on your computer, with your operating system and your version of Python. Let’s have GitHub run the tests for us automatically.

GitHub Actions are configured by workflow files. These are YAML files that live in the .github/workflows directory of your repository. GitHub automatically looks for files in that directory and runs them when the conditions you specify are met.

We’ll write the workflow by hand so that you can see what each part does. For more details than are given here, see GitHub’s Creating an example workflow tutorial.

5. Write the workflow file

  1. Create the .github/workflows directory. From the top level of your repository run:

    mkdir -p .github/workflows

    (Note the . at the start of .github! Since it starts with a ., it is a hidden directory; you’ll need to run ls -a to see it.)

  2. Use your favorite text editor to create a file called .github/workflows/tests.yml. We’ll build it up a piece at a time.

  3. First, give the workflow a name and tell GitHub when to run it. Add the following to tests.yml:

    name: Tests

on:
  push:
    branches: [main]
  pull_request:

    The name is what will show up on GitHub when the workflow runs. The on section lists the events that trigger the workflow. Here we’ve said to run the workflow whenever anything is pushed to the main branch, and whenever a pull request is opened or updated. (There are many other events you can trigger on; see Events that trigger workflows for the full list.)

    Warning

    Indentation matters in YAML! It’s how YAML knows what belongs to what. Always use spaces, never tabs, and be consistent. If your workflow doesn’t run, the first thing to check is your indentation.

  4. Next, add a job. A workflow is made up of one or more jobs, each of which runs on its own fresh computer (a runner). Add the following below what you have:

    
jobs:
  test:
    runs-on: ubuntu-latest

    test is the ID of the job; you can call it whatever you like. runs-on tells GitHub what operating system to use for the runner. Here we’re using the latest version of Ubuntu Linux that GitHub provides.

  5. Finally, tell the job what to do by giving it a list of steps. Add the following under runs-on (note the indentation: steps should line up with runs-on):

        steps:
      - name: Check out the repository
        uses: actions/checkout@v7

      - name: Set up Python
        uses: actions/setup-python@v7
        with:
          python-version: "3.13"

      - name: Install toymath and pytest
        run: |
          python -m pip install --upgrade pip
          pip install . pytest

      - name: Run the tests
        run: pytest

    Each step starts with a - and has an optional name, which is what you’ll see on GitHub. The steps run in order. There are two kinds of steps:

    • Steps with run execute commands on the command line of the runner, just like you would in your terminal. The | lets us put several commands on separate lines.
    • Steps with uses run an action: a reusable piece of code that someone else wrote to do a common task. The text after uses is the GitHub repository the action lives in followed by @ and the version to use; e.g., actions/checkout@v7 is version 7 of https://github.com/actions/checkout. Some actions take inputs, which are given in the with section.

    Remember that each job runs on a brand new computer with nothing on it. So our job has to do everything you did on your computer to run the tests:

    • actions/checkout downloads a copy of your repository onto the runner.
    • actions/setup-python installs Python (version 3.13, in this case).
    • We then use pip to install toymath and pytest. (We don’t need the -e here, since we won’t be editing the code on the runner.)
    • Finally, we run pytest. If any of the tests fail, pytest will exit with an error, which will cause the job to fail.
    CautionCheck your work: the complete tests.yml 
    name: Tests

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Check out the repository
        uses: actions/checkout@v7

      - name: Set up Python
        uses: actions/setup-python@v7
        with:
          python-version: "3.13"

      - name: Install toymath and pytest
        run: |
          python -m pip install --upgrade pip
          pip install . pytest

      - name: Run the tests
        run: pytest

6. Commit and push, then open a pull request

  1. Commit the workflow:

    git add .github/workflows/tests.yml
git commit -m "add workflow to run tests"

  2. Push your branch to your fork on GitHub. Since add-ci-tests doesn’t exist on GitHub yet, we need to tell git to create it:

    git push -u origin add-ci-tests

  3. Go to your fork on GitHub (https://github.com/YOUR_USERNAME/toymath). You should see a box saying that add-ci-tests had recent pushes. Click the green Compare & pull request button.

  4. This will open the “Comparing changes” page. Look carefully at the gray box at the top of the page. You’ll see that the “base repository” is SU-OSPO/toymath. When you create a pull request from a fork, GitHub assumes by default that you want to contribute your changes back to the upstream repository you forked from. We don’t want that here! We want to merge the changes into the main branch of your fork. To change that:

    • Click the “base repository: SU-OSPO/toymath” drop-down button and select YOUR_USERNAME/toymath.
    • The page will reload, and the gray box will now just show base: main ← compare: add-ci-tests. Make sure that base is main and compare is add-ci-tests.
    Warning

    Always double-check the base repository and branch before you create a pull request from a fork. It’s easy to accidentally open a pull request on someone else’s repository!

  5. Click the green Create pull request button.

Note

If this is the first time you’ve used GitHub Actions on your fork, you might see a message on the Actions tab saying that workflows aren’t being run on this forked repository. If so, click the green button saying “I understand my workflows, go ahead and enable them.” (GitHub disables workflows on forks by default, since you didn’t write them yourself.)

7. Look at the results

  1. Scroll to the bottom of your pull request. Just above the merge button, you’ll see a box that lists the checks on the pull request. You should see a check called Tests / test (pull_request): this is the Tests workflow, test job, triggered by the pull_request event. While it’s running it will have a yellow dot next to it. After a minute or so it should change to a green check mark, and the box will say “All checks have passed.”

  2. Click on the Tests / test (pull_request) check. This will take you to the page for that run of the job. You’ll see each of the steps you wrote in your workflow file (plus a few that GitHub adds automatically). Click on the “Run the tests” step to expand it. You’ll see the same output from pytest that you saw on your computer!

  3. You can also see all of your workflow runs by clicking the Actions tab at the top of your repository’s page on GitHub. Try that now. You’ll see a list of all your workflows on the left, and all the times they’ve run in the middle.

IV. Breaking things

Your tests pass. But how do you know that they actually test anything? Let’s see what happens when someone makes a change that breaks the code.

8. Introduce a bug

  1. Use your favorite text editor to open toymath/functions.py, and change the + in the add function to a *, so that it reads:

    def add(a, b):
    """Return the sum of a and b."""
    return a * b

    Oops.

  2. Let’s pretend that you forgot to run the tests on your computer before committing. Commit and push the change:

    git add -u
git commit -m "update add function"
git push

    (Since we used -u the first time we pushed, git push knows to push to the add-ci-tests branch on your fork.)

  3. Go back to your pull request on GitHub. Pushing to the add-ci-tests branch automatically updated the pull request, which triggered the Tests workflow again. Once it finishes, you should see a red X next to the check, and the box will say “All checks have failed.”

  4. Click on the failed check, and expand the “Run the tests” step. You’ll see that pytest tells you exactly what went wrong:

    >           assert subtract(c, a) == b
E           assert 12 == 5
E            +  where 12 = subtract(15, 3)

    Our round-trip test found that add(3, 5) returned 15 instead of 8.

Notice that GitHub still lets you merge the pull request even though the tests failed. Failing checks are a big red warning sign to anyone reviewing the pull request, though!

Tip

Many projects set up branch protection rules to prevent pull requests from being merged until all the checks pass. You can do this in your repository’s Settings, under “Rules” (or “Branches”). See GitHub’s documentation on protected branches for more details.

9. Fix the bug

  1. Open toymath/functions.py again and change the * back to a +.

  2. This time, run the tests on your computer before committing:

    pytest

    They should pass. (Try running pytest with the * in place, too, if you like. You’ll see that you could’ve caught the bug before pushing it!)

  3. Commit and push the fix:

    git add -u
git commit -m "fix add function"
git push

  4. Go back to your pull request. Once the workflow finishes running, your checks should be green again.

V. Testing on multiple operating systems and Python versions

Right now we only test on one operating system (Ubuntu Linux) and one version of Python (3.13). But people who use your package will use lots of different operating systems and versions of Python. Code that works on one doesn’t always work on another. (File paths are a common culprit: Windows uses \ to separate directories, whereas Linux and MacOS use /.)

Installing a bunch of different operating systems and versions of Python on your own computer to test all of those combinations would be a pain. With GitHub Actions it’s easy, thanks to the matrix strategy.

10. Add a matrix to the workflow

  1. Open .github/workflows/tests.yml and change the jobs section so that it reads:

    jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, macos-latest, windows-latest]
        python-version: ["3.12", "3.13", "3.14"]
    runs-on: ${{ matrix.os }}
    steps:
      - name: Check out the repository
        uses: actions/checkout@v7

      - name: Set up Python ${{ matrix.python-version }}
        uses: actions/setup-python@v7
        with:
          python-version: ${{ matrix.python-version }}

      - name: Install toymath and pytest
        run: |
          python -m pip install --upgrade pip
          pip install . pytest

      - name: Run the tests
        run: pytest

    Here’s what changed:

    • We added a strategy section with a matrix. The matrix defines two variables, os and python-version, each with a list of values. GitHub will create a separate job for every combination of these values. In this case that’s 3 operating systems × 3 Python versions = 9 jobs, all of which will run at the same time.
    • The ${{ ... }} syntax lets us use the values of variables in the workflow. We use ${{ matrix.os }} to set the operating system the job runs on, and ${{ matrix.python-version }} to set which version of Python is installed.
    • By default, if one job in a matrix fails, GitHub cancels all the others. Setting fail-fast: false tells GitHub to let them all finish. That way we can see all of the combinations that fail, not just the first one.
    Note

    Why are the Python versions in quotes? Because YAML would otherwise read them as numbers, and 3.10 (for example) would become 3.1!

  2. Commit and push the change:

    git add -u
git commit -m "test on multiple operating systems and python versions"
git push

  3. Go back to your pull request on GitHub. You’ll now see nine checks at the bottom, with names like Tests / test (macos-latest, 3.14) (pull_request). It might take a few minutes for all of them to finish (the Windows and MacOS runners are usually a bit slower to start). Click on a few of them to see the output. Go to the Actions tab too; if you click on the latest run of the Tests workflow you’ll see all nine jobs listed on the left.

11. Merge the pull request

Assuming all of the checks pass, it’s time to merge. Since we have a few “oops” commits on this branch (breaking and then fixing the add function), this is a good place to squash and merge (see the 9/17 lecture in the git unit if you need a refresher). Squashing will combine all of the commits on add-ci-tests into a single commit on main, so those “oops” commits won’t clutter up main’s history.

  1. At the bottom of your pull request, click the drop-down arrow next to the green merge button and select “Squash and merge.”

  2. Edit the commit message if you like, then click Confirm squash and merge.

  3. Click the Delete branch button to delete add-ci-tests on GitHub.

  4. Click on the Actions tab. You’ll see that the Tests workflow is running again. This is because merging the pull request pushed a new commit to main, and we told the workflow to run on every push to main. That way you’ll know if something on main ever gets broken, even if it gets there without a pull request.

NoteWorkflow templates

Writing workflows from scratch is good for understanding how they work, but you don’t always need to. GitHub provides a library of workflow templates for common tasks, such as running tests for many different languages, checking code with a linter, building and publishing packages, and deploying websites. To see them, click the Actions tab of your repository, then click the New workflow button. GitHub will suggest templates that it thinks are relevant to your repository, and you can search for others. Clicking Configure on a template opens it in GitHub’s file editor so that you can modify it before committing it.

Templates are a good starting point, but they’re not always up to date (they may use older versions of actions or of Python, for example). Now that you know what the parts of a workflow file do, you’ll be able to read a template and tweak it to fit your project.

VI. Putting it into practice: contributing to a partner’s repository

So far you’ve only opened pull requests on your own fork. In a real project, the point of CI is that it checks contributions from other people. Let’s try that out by contributing a new feature to a partner’s fork of toymath. You and your partner will each contribute to the other’s repository at the same time.

12. Add your partner’s fork as a remote

  1. Find a partner. Exchange the web addresses of your forks of toymath with each other. Your partner’s should look like https://github.com/PARTNER_USERNAME/toymath, where PARTNER_USERNAME is their GitHub username.

    Important

    Before continuing, make sure that both of you have finished step 11, so that your main branches on GitHub have the Tests workflow in them.

  2. Your local repository currently only knows about one remote repository: your fork, which is called origin. You can add as many other remotes as you like. In your terminal, add your partner’s fork as a remote called partner:

    git remote add partner https://github.com/PARTNER_USERNAME/toymath.git

    (We can use the HTTPS URL here, rather than SSH, since we’re only going to download things from your partner’s fork, not push to it.) Now run:

    git remote -v

    You should see both origin and partner listed.

  3. Download the latest changes from your partner’s fork:

    git fetch partner

    This will tell you about the branches on your partner’s fork, such as partner/main.

13. Add new functions

  1. Create a new development branch, starting from your partner’s main branch:

    git checkout -b add-mult-div partner/main

    Why start from partner/main instead of your own main? Since you and your partner both squashed and merged your CI changes, your main branches have the same files, but different commits. If you started from your own main, your pull request would include your squashed commit in addition to your new changes, making it confusing to review. Starting from partner/main ensures that your pull request contains only the new changes.

  2. Use your favorite text editor to open toymath/functions.py and add the following to the end of it:

    

def multiply(a, b):
    """Return the product of a and b."""
    return a * b


def divide(a, b):
    """Return a divided by b."""
    return a / b

  3. We also need to tell the package about the new functions so that users can import them with from toymath import multiply, divide. Open toymath/__init__.py and change it so that it reads:

    """A toy math package."""

from .functions import add, subtract, multiply, divide

__all__ = ["add", "subtract", "multiply", "divide"]

    Since the toymath_calculator program uses __all__ to decide what operations are available, you should now be able to run:

    toymath_calculator multiply 3 4

    and get back 12.0. (Recall that we installed toymath in editable mode, so you don’t need to re-install it to pick up the changes.)

CautionChallenge: Test the new functions

New code should come with new tests! Add a round-trip test for multiply and divide to tests/test_functions.py, similar to the one we wrote for add and subtract. Run pytest to make sure that your new test passes.

Hint: be careful what numbers you choose. What happens if you try to divide by zero?

CautionSolution

Change the import at the top of tests/test_functions.py so that it imports the new functions:

from toymath import add, subtract, multiply, divide

Then add the following to the end of the file:



def test_multiply_divide_roundtrip():
    """Check that dividing the product of a and b by a gives back b."""
    for a, b in [(3, 5), (-2, 7), (10, 0)]:
        c = multiply(a, b)
        assert divide(c, a) == b

Here we multiply a and b to get c, then divide c by a, which should give back b. Since we divide by a, we have to make sure that none of our values of a are zero. (It’s fine for b to be zero, though.)

Then run:

pytest

You should see 2 passed.

14. Open a pull request on your partner’s repository

  1. Once your tests pass, commit your changes:

    git add -u
git commit -m "add multiply and divide functions"

    (We can use git add -u here since we only modified files that git is already tracking.)

  2. Push your branch to your fork (remember, you can’t push to your partner’s fork):

    git push -u origin add-mult-div

  3. Go to your fork on GitHub and click the Compare & pull request button. This time, set the base repository to your partner’s fork: click the “base repository” drop-down button and select PARTNER_USERNAME/toymath. Make sure that the base branch is main, and that you’re comparing YOUR_USERNAME/toymath’s add-mult-div branch. Double-check that the “Files changed” at the bottom of the page shows only your changes to functions.py, __init__.py, and test_functions.py.

  4. Add a short description of what your pull request does, then click Create pull request.

15. Review your partner’s pull request

Your partner has now opened a pull request on your fork. Go to your fork on GitHub and click on the Pull requests tab. You should see their pull request. Click on it.

Note

For security reasons, GitHub may not automatically run workflows on pull requests from people who haven’t contributed to your repository before. If you see a message saying that workflows are awaiting approval, click Approve and run (or Approve workflows to run). In general, you should look over the changes in a pull request from a new contributor before approving its workflows, since the workflows will run the code in the pull request!

  1. Scroll to the bottom of the pull request and look at the checks. These are the nine Tests checks that you set up. GitHub is running your partner’s new code, along with your partner’s new test, on three operating systems and three versions of Python. Wait for them to finish. Do they all pass? If not, click on the failed checks to see why, and leave a comment on the pull request letting your partner know what went wrong. They can fix the problem by pushing new commits to their add-mult-div branch, which will automatically update the pull request and re-run the checks.

  2. Click on the Files changed tab to review the code. Does it look right? Did your partner include a test for the new functions? You can leave a comment on a specific line by hovering over it and clicking the blue + button that appears.

  3. When you’re satisfied with the changes, click the green Review changes (or Submit review) button in the upper right of the Files changed tab, select Approve, and click Submit review.

  4. Go back to the Conversation tab. At the bottom, click the drop-down arrow next to the merge button, select “Squash and merge,” then click Confirm squash and merge.

Congratulations! You and your partner have each contributed a new feature to the other’s repository, with CI checking every contribution along the way. This is exactly how contributions to large open source projects work.

VII. Wrapping up

Your fork’s main branch on GitHub now has new commits that your local repository doesn’t know about: your squashed CI changes, and your partner’s new functions. Let’s sync them.

  1. In your terminal, switch back to main and pull the changes:

    git checkout main
git pull

    Run ls .github/workflows. You should see tests.yml. Open toymath/functions.py; you should see your partner’s multiply and divide functions.

  2. Delete your local copies of the add-ci-tests and add-mult-div branches:

    git branch -D add-ci-tests add-mult-div

    Note that we had to use a capital -D here. That’s because the commits on these branches were squashed when they were merged, so git doesn’t see the individual commits on those branches in main. It’ll warn you that the branches aren’t fully merged if you use -d. The capital -D forces the deletion.

  3. You can also delete the add-mult-div branch on your fork on GitHub, either on the “View all branches” page or by running:

    git push origin --delete add-mult-div

  4. Finally, if you no longer need to get changes from your partner’s fork, you can remove it as a remote:

    git remote remove partner

Congratulations! Your repository now automatically runs its tests on three operating systems and three versions of Python every time someone opens a pull request, and you’ve seen how CI helps you review contributions from others. In the next tutorial we’ll use GitHub Actions to build and publish documentation for toymath.
